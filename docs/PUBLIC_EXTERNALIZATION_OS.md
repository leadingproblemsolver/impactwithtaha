# Public Externalization OS

## Observable target

A cold evaluator should be able to answer in under 90 seconds:

1. What kind of problems does Taha repeatedly work on?
2. What has actually been built or executed?
3. Which claims are reproducible, deployed, externally exercised, or still hypotheses?
4. Which two artifacts are most relevant to what I own?
5. What is the smallest consequential next action I can give him?

## Canonical compilation pipeline

```text
real work / external attempt
-> source receipt
-> evidence-state assignment
-> canonical registry
-> micro case
-> observer-specific renderer
-> distribution
-> external behavior / correction / rejection / use / payment
-> registry update
```

Presentation is downstream. It may select, compress, sequence, visualize, or personalize evidence. It may not create a stronger evidence state.

## One source, many renderers

| Surface | First job | Required payload | CTA |
| --- | --- | --- | --- |
| Portfolio home | establish parseable throughline + proof floor | identity, 3–4 receipts, boundaries, current external test | evaluate / inspect / give boundary |
| Proof map | independent technical inspection | mechanism, reproduce path, receipt, limitation | source |
| GitHub README | let a maintainer reproduce | problem, invariant, run path, tests, current receipt, next external test | issue / review / use |
| Resume | pass role-specific screen | role requirement -> owned mechanism -> receipt | interview / technical evaluation |
| LinkedIn | high-context professional discovery | one case, one visible artifact, one concrete result/boundary | inspect / discuss |
| X | live operator discovery | concrete pain -> observation -> artifact -> question/ask | reply / test |
| Direct email/DM | change one person's behavior | their workflow -> one relevant proof -> one low-friction ask | call / file / correction |
| Hackathon / judge page | rapid external judgment | problem -> demo -> architecture -> receipt -> boundary | run / judge |
| One-page PDF | offline/meeting transfer | 3 strongest proofs + QR/direct links + current ask | review / introduction |

## Featured proof rule

Homepage prominence is ordered by:

`external consequence x reproducibility x technical ownership x relevance x freshness`

Internal architecture, routers, operating systems, and meta-methods remain subordinate unless an external actor uses them.

## Case schema

Every public case should compile to:

```yaml
title:
owned_workflow:
observed_problem:
mechanism:
what_i_owned:
input:
output:
receipt:
hostile_test:
evidence_state:
boundary:
source_links:
external_actor:
behavior_change:
next_evidence_event:
```

Missing fields stay visibly missing. Do not backfill with narrative.

## Visual system

The visual identity should feel like an inspection interface:
- editorial typography;
- strong information hierarchy;
- receipt/boundary pairings;
- monospace for states, IDs, gates, and transitions;
- minimal accent color;
- no decorative project-grid logic;
- work shown as operating transitions and evidence.

## Maintenance

When new proof lands:

1. update source artifact / receipt;
2. update `ARTIFACT_REGISTRY.json` or the owning evidence record;
3. update `PUBLIC_SURFACE_MANIFEST.json` only if the artifact crosses the featured threshold;
4. regenerate or revise the micro case;
5. update the audience renderer that actually benefits;
6. distribute to a named observer/channel;
7. record external behavior;
8. promote/demote the evidence state only from receipts.

Kill presentation work when it is not linked to a concrete observer, role, buyer, reviewer, or distribution event.
